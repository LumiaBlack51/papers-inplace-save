# PDF annotation editing crash and invisible Chinese text, 2026-09-22

Status: fixed and tested at the annotation/library level; installed locally. Full user GUI sequence and real OneDrive round-trip remain unverified.

## Report and evidence

The user edited FreeText, closed editing mode, saw the text disappear, re-entered editing (text reappeared), then pressed Ctrl+S and Papers exited. The installed build was Papers 50.2, Flatpak branch `inplace-save`. Its original commit was `8f269aca6d702f7d38685903ea47936222ae5af7a749ec73097a4fe24944f7de`.

The application logged:

```text
PapersView:ERROR:../libview/context/pps-annotations-context.c:792:pps_annotations_context_remove_annotation: code should not be reached
```

TwoDrive continued running with no restart; no concurrent daemon error was found. The same assertion was reproduced against ordinary local PDFs with no TwoDrive dependency. A complete call stack for the original GUI incident was not captured, so the user's exact internal callback order is not claimed as proven.

## Causes and fixes

A deferred annotation removal can arrive after document reload or an earlier removal. Previously, the backend was modified first, then a failed model lookup aborted the process. The fix checks model membership before any backend or undo mutation.

Empty FreeText focus-out queued a widget pointer without cancelling the callback on destruction or checking whether content had been refilled. The fix tracks the idle source, cancels it in dispose, and rechecks content/deletion state at execution.

The GTK editor automatically falls back to another font for Chinese; the PDF FreeText backend uses a single selected font. A blank-page test rendered Latin text with Liberation Sans but rendered zero nonwhite pixels for Chinese. A covering CJK font produced visible text. The fix records a Pango fallback font in the annotation when it covers the complete string. Existing text is checked on entry to editing, and new text is checked on buffer changes. Size is preserved; covered Latin text keeps its original font.

## Boundaries and prevention

The full GUI close-editor/re-enter/Ctrl+S interaction has not been replayed automatically. No real cloud upload/download comparison was performed. A single fallback must cover the whole text; mixed-script, shaping, embedding and other-machine portability are not exhaustively covered. Tests do not establish recovery of unsaved text from the crashed process. Keep the lifecycle, undo, save and font regressions when modifying these paths.

The shell executable and PDF backend were retained, including the earlier Ctrl+S in-place-save patch. The source archive and original build manifest identify the corresponding sources; a full fresh Flatpak build is documented but was not run. A deb wraps the tested Flatpak with a per-user installer, without root installation hooks or automatic application closure.

## Release packaging verification

The deb payload was extracted and its Flatpak and launcher compared byte-for-byte to the release inputs. Five installer tests cover root refusal, current-commit no-op, per-user install, failed-install launch prevention, and filename argument preservation. The extracted launcher correctly skipped reinstalling the already-current application.

A separate temporary Flatpak installation successfully installed the original backup bundle, updated it to the fixed bundle, and reported the expected fixed commit. Runtime downloads were disabled for this packaging-only test (`--no-deps`); it does not validate a fresh runtime download or a graphical launch on a new machine. Flatpak 1.14 returns an already-installed error when manually reinstalling exactly the same bundle; the deb launcher checks the commit and avoids that case. No package maintainer hooks execute as root, and no user application was forcibly closed.
